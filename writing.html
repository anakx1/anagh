Troubleshooting · Rocky Linux 9

xrdp: “X server could not be started”

The xrdp service was active, the RDP connection was accepted, and the session still failed. The useful evidence was in the session log, not the unit status.

Symptom

A remote desktop login reached the session handoff, then failed with X server could not be started. A quick systemctl status xrdp showed the daemon running, which made the failure look like a desktop or authentication problem.

Evidence

systemctl status xrdp --no-pager
journalctl -u xrdp -b --no-pager | tail -n 60
tail -n 80 /var/log/xrdp.log
rpm -q xrdp xorgxrdp

The journal showed the session failing at the X server handoff. The xrdp log identified the missing backend, and the package query confirmed xorgxrdp was not installed.

Root cause

xrdp was installed without the Xorg backend. The daemon could accept connections, but it had no X server backend to start the desktop session.

Fix

sudo dnf install -y xorgxrdp
sudo systemctl restart xrdp
sudo systemctl status xrdp --no-pager

Reconnect with the RDP client and verify the desktop session starts. If it still fails, check ~/.xsession-errors and confirm the desktop session package is installed before changing SELinux or firewalld.

What I learned

  • “Active” is not the same as “working”. Check the log at the point of failure, not just the unit state.
  • On RHEL and Rocky Linux, xrdp and xorgxrdp are separate packages.
  • Read the systemd journal and the application log together: one gives the service view, the other gives the session view.

SELinux · RHEL 9

SELinux denied it. Now what?

A repeatable triage path for AVC denials: confirm enforcement, find the denial, read the source/target/class, then apply the smallest permanent fix.

1. Confirm the mode

getenforce
sestatus

Do not start with setenforce 0. If you need permissive mode to test a hypothesis, set it temporarily and put it back as part of the test.

2. Find the denial

sudo ausearch -m AVC,USER_AVC -ts recent
sudo ausearch -m AVC -ts recent | audit2allow -w
sudo sealert -a /var/log/audit/audit.log

sealert is available when setroubleshoot-server is installed. The important fields are the source context, target context, and object class. For example: httpd_t trying to read a file labeled var_t instead of httpd_sys_content_t.

3. Inspect labels, not just permissions

ls -Zd /var/www/html /web
ps -eZ | grep httpd
sudo semanage fcontext -l | grep -E '/web|/var/www'

Standard Linux permissions can be correct while the SELinux label is wrong. If the service account can read the file with sudo -u apache cat /web/index.html but the web request is denied, start with labels.

4. Choose the smallest fix

Wrong file label: add a persistent file-context rule, then relabel the tree.

sudo semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?"
sudo restorecon -Rv /web

Boolean: enable only the capability the service needs.

sudo getsebool -a | grep httpd
sudo setsebool -P httpd_can_network_connect on

Non-standard port: label the port instead of disabling the policy.

sudo semanage port -a -t http_port_t -p tcp 8080
sudo semanage port -l | grep http_port_t

5. Verify and document

sudo ausearch -m AVC -ts recent
sudo systemctl restart httpd
curl -I http://localhost:8080

Do not ship: setenforce 0, chmod 777, or a broad custom policy when a label or boolean solves the problem. audit2allow is for a genuinely custom policy, not for fixing mislabeled files.

What I learned

  • SELinux is a labeling system. The denial tells you which source context was denied access to which target context and class.
  • Persistent fixes use semanage plus restorecon; a one-off chcon is useful for testing, not for configuration management.
  • Disabling enforcement hides the evidence. Use permissive mode briefly to confirm, then return to enforcing.

Storage · LVM / XFS

The LVM extend that didn’t take

lvextend can return success while df -h stays flat. Check the stack from disk to filesystem before resizing again.

The failure pattern

Either lvextend reports success and df -h shows the old size, or it fails with insufficient free space. Both are layer problems: the logical volume, the volume group, the physical volume, or the filesystem.

1. Map the stack

lsblk
sudo pvs
sudo vgs
sudo lvs
df -hT

Read it bottom-up: disk → partition → physical volume → volume group → logical volume → filesystem. df is the final proof, not lvextend.

2. Check free extents

sudo vgs
sudo lvs -o lv_name,vg_name,lv_size,seg_size,seg_count

If VFree is zero, the volume group has no room. Expand the underlying disk or partition and run pvresize, or add another physical volume.

3. Grow the LV and filesystem together

sudo lvextend -r -L +10G /dev/vg/lv
df -hT /mountpoint

The -r flag calls the filesystem grow tool. If you omit it, grow the filesystem explicitly:

# XFS
sudo xfs_growfs /mountpoint

# ext4
sudo resize2fs /dev/vg/lv

4. If the disk was expanded, resize the PV too

sudo growpart /dev/vda 3
sudo pvresize /dev/vda3
sudo lvextend -r -l +100%FREE /dev/vg/lv
df -hT /mountpoint

Confirm the device and partition number with lsblk first. growpart and pvresize are the steps people skip when a hypervisor disk was enlarged.

What I learned

  • lvextend changes the logical volume; it does not always grow the filesystem. -r is the safer habit.
  • Always run df -hT after the resize. The command that returns success is not the command that proves capacity.
  • Take a snapshot before destructive storage work, and record the before/after output for the ticket or write-up.

Hardening · RHEL 9

SSH and firewalld hardening

Key-only SSH is more than setting PasswordAuthentication no. The effective sshd policy, the firewall, and the SELinux port label all have to agree with the port clients use.

Symptom

On a RHEL 9 guest, SSH can be reachable while the effective policy is still broader than the intended key-only, non-root access. The service looks healthy, so the gap is easy to miss unless the sshd policy, listening socket, firewall zone, and SELinux port label are checked together.

Evidence

sudo sshd -T | grep -Ei '^(port|permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|allowusers)'
sudo ss -tlnp | grep sshd
sudo firewall-cmd --list-all
sudo semanage port -l | grep ssh_port_t

sshd -T prints the effective configuration after includes, so it is the check that matters. ss shows the listening socket, firewall-cmd --list-all shows the active zone, and semanage port -l shows whether SELinux allows sshd to bind the chosen port.

Root cause

The common root cause is a partial change: sshd_config is edited but not reloaded, the firewall still allows the old service, or SELinux has no label for the new port. Any one of those leaves the guest either more open than intended or unreachable on the new port.

Fix

Confirm key-based access works for the account that should retain access. Keep a second SSH session open before reloading sshd; it is the recovery path if the new policy locks you out.

install -d -m 700 ~/.ssh
vi ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
sudo restorecon -Rv ~/.ssh

Add an explicit drop-in. RHEL 9 includes /etc/ssh/sshd_config.d/*.conf, so keep the policy small and readable:

sudo vi /etc/ssh/sshd_config.d/50-hardening.conf
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
AllowUsers anagh

Replace anagh with the account that should be allowed. If the port is changing, add Port 2222 to the same drop-in; otherwise keep the default port. Validate the file before touching the running service:

sudo sshd -t

If the SSH port changes, update SELinux and firewalld before reloading sshd. The example uses port 2222; use the port you actually configured.

sudo semanage port -a -t ssh_port_t -p tcp 2222
sudo semanage port -l | grep ssh_port_t

If the port is already defined, replace -a with -m. Then move the firewall rule from the default ssh service to the new port and reload:

sudo firewall-cmd --permanent --remove-service=ssh
sudo firewall-cmd --permanent --add-port=2222/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

If you keep SSH on port 22, add the service instead of a port:

sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

Reload sshd only after the port is allowed by SELinux and firewalld. Keep the second session open until a fresh connection succeeds. The verification below assumes port 2222; substitute 22 if you kept the default.

sudo systemctl reload sshd
sudo sshd -T | grep -Ei '^(port|permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|allowusers)'
sudo ss -tlnp | grep ':2222'
sudo firewall-cmd --list-all
ssh -p 2222 anagh@host

What I learned

  • sshd -T is the effective configuration; the file on disk is only one input after includes are applied.
  • Keep a second session open until a new SSH policy has been tested from a fresh connection.
  • SSH hardening is three layers: sshd policy, firewalld, and SELinux port labels. A change to one layer has to be checked against the other two.
  • Use sshd -t before a reload and verify with ss -tlnp after it; a service that reports active is not proof that the intended port is listening.

Apache · RHEL 10

Custom web root and port on RHEL: the four layers

Moving Apache to /web/http on port 8282 is four changes: httpd config, SELinux file context, SELinux port, and firewalld. Missing one layer leaves the other three looking correct.

Symptom

The new document root or port is not live even though one layer has been changed. A 403 from /web/http, a connection failure on 8282, or the default page still answering means at least one of the remaining layers still points at the old path or port.

Evidence

sudo httpd -t
grep -nE '^(Listen|DocumentRoot)' /etc/httpd/conf/httpd.conf
ls -ldZ /web/http
sudo semanage fcontext -l | grep /web/http
sudo semanage port -l | grep http_port_t
sudo firewall-cmd --list-all
sudo ss -tlnp | grep ':8282'
curl -I http://localhost:8282

Root cause

The four layers are independent. httpd.conf controls the path and port Apache asks for, the SELinux file context controls file access, semanage port controls whether httpd may bind 8282, and firewalld controls whether clients can reach it. Changing one layer does not update the other three.

Fix

Create the custom document root and update both the listening port and the directory policy in httpd.conf:

sudo mkdir -p /web/http
sudo vi /etc/httpd/conf/httpd.conf
Listen 8282
DocumentRoot "/web/http"
<Directory "/web/http">
    Require all granted
</Directory>

Register the SELinux file context, then apply it from the policy database:

sudo semanage fcontext -a -t httpd_sys_content_t "/web/http(/.*)?"
sudo restorecon -Rv /web/http
ls -ldZ /web/http

Allow httpd to bind the custom port:

sudo semanage port -a -t http_port_t -p tcp 8282
sudo semanage port -l | grep http_port_t

Open the port in firewalld, validate the Apache configuration, and restart the service:

sudo firewall-cmd --permanent --add-port=8282/tcp
sudo firewall-cmd --reload
sudo httpd -t
sudo systemctl enable --now httpd
sudo systemctl restart httpd
curl http://localhost:8282

Verify the listener and the active firewall zone:

sudo ss -tlnp | grep ':8282'
sudo firewall-cmd --list-all

What I learned

  • A custom web root and port is four layers, not one config file: httpd, SELinux file context, SELinux port, and firewalld.
  • semanage fcontext only registers the policy; restorecon applies the label to disk.
  • semanage port and firewalld are separate controls. Both must allow the new port before the service is reachable.
  • Validate with httpd -t before restarting, then verify with curl, ss -tlnp, and firewall-cmd --list-all.
